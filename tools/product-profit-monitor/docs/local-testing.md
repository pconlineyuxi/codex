# 本地测试与真实数据接入

## 离线验收

运行 pytest，覆盖数据查询、规则、利润分解、SQLite 生命周期、发送不明处理、纽约时区日程和页面交互。页面中演示巡查只写本地 `.runtime`，不连接公司数据库、不发送飞书。不要把演示成功当成真实数据验收通过。

业务问题页输入与演示 SKU 对应的范围。若范围包含 `DEMO-COST`，利润分解会明确阻止缺失成本被当成零；选择 `DEMO-HEALTHY` 或 `DEMO-SHIP` 可体验可复核的差异贡献。

## 手动真实数据测试

在页面选择“真实数据测试（只读）”，限定单店铺和最多 7 天，直接读取数据库。此入口无需伪造刷新凭据；其 `query_complete` 表示未触发读取截断，但 `complete=false`，不能成为正式巡查或恢复证据。结果是源金额与源日期口径，币种、日期时区和刷新完整性仍待验证；不会自动通知。正式巡查的完整性门槛不变。

## 实际数据库契约

`DATABASE_URL` 应为 PostgreSQL 只读角色。程序使用只读事务、60 秒 statement_timeout，并按单日查询；每个单日最多读取 MAX_RESULT_ROWS+1 以检测截断，超限则整次检查未完成，需缩小计划平台/店铺范围。该限制不是“只检查前 5 万条”。查询期间刷新凭据改变也会使检查失败。

接入前核对结果视图每行的真实含义、重复可能性、订单/广告字段来源、费用符号、零值与空值、币种是否统一、date_order 的时区。当前成本公式是来源记录单价与数量逐行计算后再汇总；异常详情说明为来源记录/订单-SKU 证据，不假装存在未验证的订单行 ID。

只有业务例外规则已通过真实样本检查，才能勾选真实巡查计划的规则确认。旧规则阈值是起点，不是已经验证的业务标准；bundle 等未被字段表达的例外不能靠文字提醒自动排除。

## 刷新凭据

由数据刷新任务在所有相关提交完成后原子写入 `PROFIT_READY_FILE`。以下仅为结构示例，不可直接作为真实就绪凭据：

```json
{
  "status": "complete",
  "snapshot_id": "unique-refresh-run-id",
  "source": "bi.ba_mv_profit_order_line_and_ad_info",
  "coverage_start": "2026-09-01",
  "coverage_end": "2026-09-09",
  "refreshed_at": "2026-09-09T12:00:00Z",
  "timezone": "America/New_York",
  "currency": "USD",
  "currency_normalized": true
}
```

coverage_end 为不包含的右边界。刷新未开始/进行中时必须撤销旧凭据或改成非 complete 状态，避免查询跨越刷新提交但仍读取相同凭据。若刷新系统不能遵守这个契约，继续影子/离线验证，不启用正式巡查。超过最大凭据年龄、缺少覆盖范围、空结果尚未核实等情况不允许自动恢复异常。旧窗口长期未覆盖会持续保持待核查，不自动关闭。

核实以上条件后才设置 `PROFIT_LIVE_CONTRACT_CONFIRMED=yes`。这不是绕过验证的开关，而是接入人完成契约核对的记录。

## 飞书联调

默认 `FEISHU_ENABLED=false`。需配置 FEISHU_APP_ID/FEISHU_APP_SECRET，核实应用可向 Yuxi 私聊的 open_id，再设置 `FEISHU_RECEIVER_CONFIRMED=Yuxi`。工具详情地址 MONITOR_PUBLIC_URL 要求 HTTPS，应置于公司认证后。真实计划需关闭影子运行才会产生待发通知。不要使用 webhook 群机器人替代私聊目标。

未部署 HTTPS 页面前可以验证队列及 mock 发送器；本地 localhost 链接不适合作为手机可访问的正式通知入口。发送超时、连接中断或结果不明标为 uncertain，不盲目重发；需在飞书与队列核对后处理。已确定失败可由 worker 重试。

## 部署前剩余验收

- 核对实际来源、币种/时区、正常样本及异常样本，记录误报和漏报。
- 比较人工定位时间和工具结果，确认使用价值。
- 确认刷新状态接口、回补窗口、只读角色、公司认证、HTTPS 和备份/证据保留周期。
- 验证真实飞书收件人与访问链接后，再启用生产通知。
- 第一版不会修改业务数据；实际根因需要上游来源接入后逐步增加证据查询模板。
